# Visual baseline provenance — platform-control admin

Every image in this directory is an assertion about what the admin looks like.
This file records where each one came from.

## Why this directory exists here (#913)

The admin's only pixel baseline used to live under
`legal-search/frontend/e2e/visual.spec.ts-snapshots/`, captured by a test in that
surface's `visual.spec.ts`. Two costs, both measured:

| Cost | Evidence |
|---|---|
| A PNG has no merge strategy, so two branches touching admin layout collide on a binary file neither can merge | PRs #902 and #905 |
| An admin change broke a **legal-search** CI job, undiscoverable from the admin tree | #895 |

The second is the worse one. The failing job named a surface the author had not
opened, so the signal arrived attached to the wrong cause.

A surface owns its own baselines, its own ledger and its own CI job.
`scripts/check_visual_baseline_provenance.py` guards **both** directories — the
move would otherwise have been a downgrade, leaving admin baselines re-blessable
with no record at all. `test_every_snapshot_dir_on_disk_is_guarded` in
`scripts/tests/test_check_visual_baseline_provenance.py` fails if a snapshot
directory appears on disk and is not listed in that script's `SNAPSHOT_DIRS`.

## Why a ledger at all (#611)

For most of this repo's life baselines were regenerated by running
`--update-snapshots` on a workstation and committing the output. Three separate
times that captured a live bug and shipped it as the definition of correct — the
legal-search ledger tabulates all three. None of it ever failed CI, because a
project-level `maxDiffPixelRatio: 0.06` licensed ~86,000 pixels of drift on a
1600x900 full-page shot. The suite could not go red, and its greenness was read
as evidence.

Two things keep that gone here:

1. **Zero tolerance** — `playwright.config.ts` sets no `maxDiffPixelRatio`, so
   `toHaveScreenshot` runs at Playwright's default: zero differing pixels.
2. **This ledger** — the guard fails CI and pre-commit if a `*.png` here changes
   without an entry below naming it, with a real `Reason:`.

## How to regenerate

**Preferred — let CI do it.** Add the `visual-baseline-refresh` label to your PR,
then push. The `admin-visual-baseline-refresh` job in
`.github/workflows/platform-control.yml` regenerates on `ubuntu-latest`, the same
runner that verifies, and appends an entry here automatically. You still have to
write the `Reason:` line before merging — the guard fails on the placeholder.

This matters more than it sounds. Font rasterisation differs between machines; a
baseline blessed on a workstation encodes that workstation's text rendering, which
no other machine reproduces byte-for-byte. Zero tolerance is only sustainable when
generation and verification share an environment.

**Local regeneration** is `ADMIN_E2E_PORT=<free port> npm run e2e:visual:update`.
Add an entry below by hand if you do it. Note that `reuseExistingServer` is
opt-in here (`PLAYWRIGHT_REUSE_SERVER=1`) and the run stamps its dev server with a
nonce it verifies, so this surface cannot silently photograph another worktree's
build — the trap that produced all three bad legal-search baselines.

A `Reason:` of "the tests were red" is not a reason. That is the mechanism this
file exists to catch.

## 2026-09-11 — PR #985 — CI-generated refresh

- Generated by: `admin-visual-baseline-refresh` on `ubuntu-latest` ([run](https://github.com/philipplukas/evidara/actions/runs/34594942168))
- Requested by: @philipplukas
- Source commit: `0b6dc3c7e889050089d469e0841051936543f5e5`
- Reason: the "Why nothing happened" panel changed what it says about a **running**
  run, and that is the whole point of #950.

  `e2e/visual.spec.ts:52` renders a run that is still in flight. The old baseline
  shows it diagnosed with a stall cause — the branch fired on
  `lifecycleEvents === 0 && projection === "pending"`, which is true of every run
  before DI has emitted anything, so a perfectly healthy young run was told to go
  debug a projection bridge that was never involved.

  The new baseline shows `too_early_to_diagnose`, rendered as a non-finding rather
  than a degraded chip, because "the run has not got far enough to say" is an
  honest answer and a stall cause is not.

  **What a reviewer should check in the diff:** the panel on the run that is still
  running no longer carries a red/degraded stall chip, and its text says the run is
  too early to diagnose. Everything else on the page — header, pills, metadata grid,
  evidence panels — is unchanged. If anything outside that panel moved, this
  baseline is wrong.
- Files:
  - run-detail-v2-chromium-linux.png

## 2026-09-09 — #913 — admin baseline moved out of legal-search

- Generated by: `ADMIN_E2E_PORT=3010 npm run e2e:visual:update` on a Linux
  workstation (Playwright 1.59, chromium, Node 22.23.1), against the admin's own
  `webServer` with the identity nonce verified.
- Requested by: @philipplukas
- Source commit: the commit that adds `platform-control/admin/e2e/visual.spec.ts`.
- Files:
  - run-detail-v2-chromium-linux.png
- Reason: this is a NEW baseline, not a re-bless. It replaces
  `admin-run-detail-v2-{linux,darwin}.png`, which was deleted from
  `legal-search/frontend/e2e/visual.spec.ts-snapshots/` in the same change.

  The image cannot be carried over byte-for-byte, and that is not a shortcut being
  taken: the old capture was rendered by a dev server the *legal-search* Playwright
  config started, which injects `NEXT_PUBLIC_USER_ROLE`,
  `NEXT_PUBLIC_ADMIN_ALLOWED_ROLES` and `NEXT_PUBLIC_LEGAL_SEARCH_URL` into the
  admin build. The admin's own config injects none of them, so the deep-link
  branch in the run-detail sections renders differently by construction. A capture
  under zero tolerance had to be retaken.

  What a reviewer should check in the new image, all of it visible in the
  full-page shot: the run header (`Run run_01`, Running / Production pills), the
  Operator actions card, the **Decision support** quadrant — one full-width
  `WHY THIS MATTERS` card above three equal subordinate cards
  (`WHAT IS BLOCKED` / `WHAT CHANGED RECENTLY` / `IF YOU DO NOTHING`) — the 13-field
  metadata grid, the acceptance-evidence panel, the capture ledger, Pipeline Health
  with four stages in four distinct states (ok / in progress / pending / pending),
  and the seven collapsed accordion triggers below it.

  What must NOT have changed: the decision quadrant's hierarchy. The primary card
  is full-width and visually dominant; the three subordinate cards sit in one row
  at md+ and are equal in weight to each other. That hierarchy is the thing this
  baseline exists to hold, and it is invisible to every Vitest test on this surface
  because jsdom has no layout engine.

  Coverage is strictly greater than the image it replaces: the old capture framed
  the same page, and the new one additionally holds the four-state stage list, the
  acceptance-evidence panel and the capture ledger, because the mock now serves a
  populated `pipeline-health` payload rather than a bare one.

  Known limitation, stated rather than hidden: this image was generated on a
  workstation, not on `ubuntu-latest`. Under zero pixel tolerance it may not match
  the CI runner's font rasterisation on the first run. If `admin-visual-regression`
  fails on this baseline for that reason, apply the `visual-baseline-refresh` label
  and push — do not widen the tolerance, and do not bless a CI-produced image
  without checking it against the list above.
